Reading Beej's Guide to Network Programming.https://beej.us/guide/bgnet/pdf/bgnet_usl_c_1.pdf
There are several types of Internet sockets. In the guide 2 are mentioned: Stream Socket and Datagram Socker (SOCK_STREAM && SOCK_DGRAM).
Datagram sockets are sometimes called "connectionless sockets"... even though they sometimes can be connect()... programming...

Stream sockets provide reliable, two-way, connected communication streams. For example, if you send two items into a socket like "1" and "2", they will arrive on the other end in the same order: "1" followed by "2".

They are used in applications like Telnet or SSH, which allow remote connections to another computer. These applications require that characters (such as commands or passwords) arrive in the correct order, with no data loss.

Stream sockets achieve this reliable transmission by using the TCP protocol (Transmission Control Protocol). Part of the TCP/IP Network Model.

For Datagram Sockets the situation is a little bit different. When you sent Datagram socket it might arrive.... or not and even IF it arrives it might arrive in the incorrect order.
How they achieve this great result? UDP protocol (User Datagram Protocol). Follows the same network model as TCP (both use IP for routing). There is no need to confirm if packet arrived.
The most important is just build the packet and send it. In cases such as gaming, streaming, calls few packet loss doesnt really matter, what matters is speed.
(there are some additional protocols that can be used on top like tftp and dhcpcd. Used to transfer binary applications. For example require to get confirmation that packet was received "ACK" packet)

Data Encapsulation. Packet is created, wrapped ("encapsulated") in a header by first protocol, then encapsulated again by next protocol etc. till last layer.
[Ethernet[IP[UDP[TFTP[DATA]]]]]
When packet is received - hardware strips the Ethernet header, the kernel strips the IP and UDP headers, TFTP program strips the TFTP header and the data are here.

There are 2 main network models TCP (practical) and OSI (Open system interconnect for theoretical).
The TCP/IP Network model is a set of rules (or layered architecture) that ensures communication between different computers is possible. Its layers are:
5) Application Layer – Interfaces for user-level communication (e.g., HTTP, SSH, FTP)
4) Transport Layer – Ensures reliable or fast delivery (e.g., TCP for reliability, UDP for speed)
3) Network Layer – Handles addressing and routing (e.g., IP, routers, global IP addresses)
2) Data Link Layer – Deals with local network delivery (e.g., switches, MAC addresses)
1) Physical Layer – Covers the physical medium (e.g., cables, Wi-Fi, electrical signals)
*First and second layers is usually combined in 1 Physical.

OSI shares the same layers with the change in Application layer. Presentation and Session are added as 5 and 6 Layers.

Encapsulation is done automatically when using function send() for stream socket. For datagram socket sendto() is used to send socket but might require manual additional encapsulation with UDP header.

IP Addresses, structs and Data Munging

IPv4 looks like 192.0.2.111.
IPv6 looks like 2001:0db8:c9d2:aee5:73e3:934a:a5ae:9551 (sometimes if it has 0000 it can be shorten to just :).

The address ::1 or 127.0.0.1 is the loopback address (the machine that is running right now).
There is an IPv4-compatability mode for IPv6 addresses - for example 192.0.2.33 becomes ::ffff:192.0.2.33

Subnets
For organization reasons we "divide" IP address to 2 parts - network portion and host portion. Example with 192.0.2.12 we could say that first three bytes are the network and last byte is the host.
The network portion of the IP is described as netmask, which can be bitwise AND with the IP address to get the network number out of it. The netmask is usually 255.255.255.0.
The new style is to add number of network bits in decimal like 192.0.2.12/30.

Port Numbers
Beside IP addresses both TCP and UDP protocol use port number. It's a 16-bit number that's like the local address for the connection.
We need port for the computer to realise to which application connection/packet belonds to. We cant just use IP because 1 device with the same IP can run multiple applications.
cat /etc/service shows the ports.

Byte order.
Computer can store bytes with 2 styles. For the byte b34f in Big-Endian (Network Byte Order) it's b3 4f and in Little-Endian (Host Byte Order) 4fb3.
It's important when we send numbers. When server reads the message it should convert it from Network to Host with ntohl/ntohs (s for short and l for long) in C. When client send it it should convert it with Host to Network htons()

Before numbers go out we send to Network Byte Order  ntohs() or ntohl()
When they come we conver them to Host Byte Order htons() or htonl()
*function will check if transformation is needed, if yes perfoms it.

bind()
Once the socket is created we can associate that socket with a port on your local machine. This is done when the next step is to listen for incoming connections.

#include <sys/types.h>

bind specifies IP + port to the specific file descriptor created by socket.

listen() - when we want to wait for incomming connections and handle them in some way. This is the first step of the process. Second one is accept().

int listen(int sockfd, int backlog);
backlog is the number of connections allowed on the incoming queue. Incoming connections are going to wait in this queue until accept() is called.
Most system limit it to 20.
Before listening for any connections we need to bind() connections to the socket to which we are listening.
getaddinfo();
socket();
bind();
listen();
->accept(); // I assume we might add conditions for the accept.

accept() second step when waiting for incomming connection.
when somebody tries to connect() to my machine on port that i am listen() it will be put in queue (specified in the listen backlog). Once i accept this connection i will provide completely new socket in return.
Originall one still lsitens for new connections but the new one is able to send() and recv().
#include <sys/types.h>
#include <sys/socket.h>
int accept(int sockfd, struct sockaddr *addr, socklen_t *addrlen);

sockfd is the listen() socket. 
addr pointer to local struct sockaddr_storage. New information about incomming connection will be stored.
addrlen is local integer that should be set to sizeof(struct sockaddr_storage) before its address is passed to accept().



#include <string.h>
#include <sys/types.h>
#include <sys/socket.h>
#include <netdb.h>

#define MYPORT "3490" // the port users will be connecting to
#define BACKLOG 10    // how many pending connections queue will hold

int main(void)
{
    struct sockaddr_storage their_addr;
    socklen_t addr_size;
    struct addrinfo hints, *res;
    int sockfd, new_fd;

    // !! don't forget your error checking for these calls !!

    // first, load up address structs with getaddrinfo():
    memset(&hints, 0, sizeof hints);
    hints.ai_family = AF_UNSPEC;     // use IPv4 or IPv6, whichever
    hints.ai_socktype = SOCK_STREAM;
    hints.ai_flags = AI_PASSIVE;     // fill in my IP for me

    getaddrinfo(NULL, MYPORT, &hints, &res);

    // make a socket, bind it, and listen on it:
    sockfd = socket(res->ai_family, res->ai_socktype, res->ai_protocol);
    bind(sockfd, res->ai_addr, res->ai_addrlen);
    listen(sockfd, BACKLOG);

    // now accept an incoming connection:
    addr_size = sizeof their_addr;
    new_fd = accept(sockfd, (struct sockaddr *)&their_addr, &addr_size);

    // ready to communicate on socket descriptor new_fd!
}
